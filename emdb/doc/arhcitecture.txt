@ApplicationScoped          
RunIngestService implements RunIngestUseCase {

  @Inject
  MediaCatalog mediaCatalog;
  
  @Inject
  MediaSource mediaSource;
  
  @Override
  public void run(RunIngestCommand command) {
  
    MediaDetails details = mediaSource.fetch(ingest.target());
    
    CatalogRef ref = mediaCatalog.load(details);
  }
}

public sealed interface MediaDetails permits MovieDetails, PersonDetails, SeriesDetails {
  SourceId sourceId();
  MediaType type();
  String displayName();
}

public interface MediaSource {

  MediaDetails fetch(IngestTarget target);
}

@ApplicationScoped
public class TmdbMediaSource implements MediaSource {

  @Override
  public MediaDetails fetch(IngestTarget target) {
    String id = target.sourceId().value();
    try {
      return switch (target.type()) {
        case MOVIE -> toMovie(api.movie(id));
        case PERSON -> toPerson(api.person(id));
        case SERIES -> toSeries(api.series(id));
      };
    } catch (WebApplicationException e) {
      throw translate(e, target);
    } catch (ProcessingException e) {
      throw new MediaSourceException.Unavailable("TMDB unreachable for " + target, e);
    }
  }
}

public interface MediaCatalog {

  CatalogRef load(MediaDetails details);
}

@ApplicationScoped
public class MediaApiCatalog implements MediaCatalog {

  @Inject
  SaveMovieUseCase saveMovie;
  
  @Inject
  SavePersonUseCase savePerson;  
  
  @Inject
  SaveSeriesUseCase saveSeries; 
  
  switch (details) {
    case MovieDetails movie -> saveMovie.save(toCommand(movie));
    case PersonDetails person -> savePerson.save(toCommand(person));
    case SeriesDetails series -> saveSeries.save(toCommand(series));
  });
}

Show me the package structure for a Quarkus module using Jakarta Data and DDD + Hexagonal architecture that performs 
CRUD operations on a Movie aggregate that has several fields. The aggregate will carry three identifiers, a surrogate 
UUID assigned by the application for equals and hashCode, a public id like “mv_1” where the number is a database 
sequence and the primary key as Long, and the Integer TMDB id. The aggregate will also have a version corresponding to 
@Version on the entity. The write operations, save, update, and delete, will be handled via REST. The save operation is 
an upsert and idempotent with respect to the external TMDB id. There is no need for any retry logic so the 
transactional boundary should be in the service. I need an audit log (no Envers) that persists the operation (ADDED, 
UPDATED, DELETED) performed on each mutable field. The read operations will be handled via GraphQL. Follow hexagonal 
purity so no ports or services are in the domain.
